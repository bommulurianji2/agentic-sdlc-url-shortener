## 1. High-Level Architecture

│  │  - Analytics               │     │  - orchestrator.py            ││
│  │  - Security validation     │     │  - graph.py / state.py        ││
│  │  serves reviewer traffic   │     │  - 7 agents                   ││
│  │  on :8000                  │     │  - retry/rollback/replanning  ││

│              └────────────────┬───────────────────┘                │
│                                ▼                                    │
│                    SQLAlchemy + Alembic                             │

## 3. API Architecture

- Versioned prefix `/api/v1` for the JSON API (FR-01, FR-03, FR-04, FR-06, FR-07); bare `/{short_code}` for redirect (FR-02) since short links must be short — no `/api/v1` prefix on the public-facing link itself.
- `/health`, `/docs`, `/redoc`, `/openapi.json` at root, auto-generated by FastAPI.
- Every error response follows the single structured contract in §16 of the master brief (`error.code`, `message`, `correlation_id`, `details`). Correlation ID is generated per request (middleware) and threaded through to logs.
- Request/response schemas are Pydantic models — this is also the OpenAPI source of truth, so `docs` and `openapi.json` stay accurate by construction, not by hand-maintenance.

## 4. Workflow Architecture

### 4.1 Two vocabularies, by design, not by accident

The master brief gives two different lists: a **state enum** (§10 — `ANALYSING`, `PLANNED`, `DESIGNING`, …) and a **graph node list** (§9 — `REQUIREMENT_ANALYSIS`, `TASK_DECOMPOSITION`, `ARCHITECTURE_DESIGN`, …). These aren't contradictory — the data model (§15) confirms it by giving `workflow_runs` **both** a `Status` column and a separate `Current stage` column. So:

- **`status`** (coarse) = one of the §10 states — what a reviewer skimming a list of runs wants to see.
- **`current_stage`** (fine) = the exact §9 graph node — what the orchestrator actually uses to decide what runs next.

Mapping (this is the part the master brief leaves implicit — making it explicit here so Phase 5 has zero ambiguity):

| status (coarse) | current_stage(s) (fine) |
|---|---|
| CREATED | *(before START)* |
| ANALYSING | REQUIREMENT_ANALYSIS, REQUIREMENT_VALIDATION |
| WAITING_FOR_REQUIREMENT_APPROVAL | HUMAN_GATE_REQUIREMENTS (pending) |
| PLANNED | TASK_DECOMPOSITION (complete) |
| DESIGNING | ARCHITECTURE_DESIGN, ARCHITECTURE_VALIDATION |
| WAITING_FOR_ARCHITECTURE_APPROVAL | HUMAN_GATE_ARCHITECTURE (pending) |
| IMPLEMENTING | IMPLEMENTATION, TEST_DESIGN (parallel), JOIN |
| TESTING | TEST_EXECUTION |
| REVIEWING | SECURITY_REVIEW, DOCUMENTATION, RELEASE_READINESS |
| RETRYING | RETRY_EVALUATION → back to IMPLEMENTATION |
| ROLLING_BACK | ROLLBACK |
| REPLANNING | re-entry at the first stale node identified by the replanning module |
| WAITING_FOR_RELEASE_APPROVAL | HUMAN_GATE_RELEASE (pending) |
| RELEASE_READY | *(gate passed, pre-COMPLETE)* |
| COMPLETED | COMPLETE |
| REJECTED | *(any gate rejected)* |
| SAFE_STOPPED | SAFE_STOP |
| FAILED | *(uncontrolled exception — distinct from SAFE_STOPPED, which is a controlled policy decision)* |

### 4.2 Corrected workflow graph

The master brief's own §9 diagram omits a fail path out of `SECURITY_REVIEW`, even though §12 requires a critical security finding to trigger `SAFE_STOPPED`. Per your confirmation, the graph implemented in `agentic/graph.py` adds it:

```
...
TEST_EXECUTION
   |
 PASS ────────────────────────► SECURITY_REVIEW ──┬── pass ──► DOCUMENTATION → RELEASE_READINESS → HUMAN_GATE_RELEASE → COMPLETE
   |                                                ├── non-critical finding ──► RETRY_EVALUATION (bounded retry, same policy as test failures)
 FAIL ──► RETRY_EVALUATION                          └── critical finding ──► SAFE_STOP
   |
  (unchanged: retry → IMPLEMENTATION, exhausted → ROLLBACK → SAFE_STOP)
```

This is the one deliberate deviation from the literal master-brief diagram in this codebase, and it's called out here plus in ADR-007 so it's never mistaken for an implementation bug.

### 4.3 Parallel branch and join (ORCH-09)

`IMPLEMENTATION` and `TEST_DESIGN` run concurrently via a `ThreadPoolExecutor` within the single process — both agents are deterministic and fast (no real CPU-bound or I/O-bound work justifying separate worker processes/queues). An explicit join waits for both before `TEST_EXECUTION` starts. See ADR-010.

### 4.4 Execution model: synchronous, resumable CLI runs (ORCH-06)

There is no long-running daemon. A scenario is driven by a script (e.g. `scripts/run_greenfield.py`) that runs the orchestrator loop **synchronously to completion or to the next pending gate**, persists `workflow_runs`/`workflow_events` at every transition, and exits. Reaching a `WAITING_FOR_*_APPROVAL` state simply means the process exits normally with that status persisted. Running `scripts/approve_gate.py` records the approval; re-running the scenario script re-loads persisted state and resumes from exactly where it left off. This satisfies "stateful" and "resumable" without needing a background worker, matching the no-overengineering constraint. See ADR-009.

## 5. Data Architecture

Two entity groups in one SQLite file (ADR-003):

**Application:** `short_urls` (1) —< `click_events` (many). Optimistic-concurrency `version` column on `short_urls` guards concurrent status/expiry updates; `click_count`/`last_accessed` updates use an atomic SQL `UPDATE ... SET click_count = click_count + 1` (NFR-09), not read-then-write.

**Orchestration:** `workflow_runs` (1) —< `workflow_events` (many); `workflow_runs` (1) —< `artifacts` (many); `workflow_runs` (1) —< `approvals` (many). Every row in every orchestration table carries `workflow_id`, giving TRACE-01/02/04 for free from the schema shape, not extra plumbing.

Full column-level detail (types, constraints, indices) is Phase 5's job — this section fixes the entity relationships and the one architecturally-significant point above (atomic counters) so Phase 5 doesn't have to re-derive it.

## 6. Security Architecture

- NFR-01/02 enforced in `app/services/url_safety.py` (Phase 2 §5) — pure function, unit-testable in isolation, called once at creation time (not re-checked on redirect, since the destination is fixed at creation and re-validating on every redirect would need a live DNS lookup per click, which is unnecessary cost for a prototype and out of scope).
- Secrets: environment variables only, `.env.example` committed, `.env` gitignored, no secret ever appears in a log line or an agent's stored artifact.
- Error responses never carry a stack trace or raw exception text — only `code`/`message`/`correlation_id`; the real exception is logged server-side, keyed by the same correlation ID.
- **Agent action controls (§6 master brief) — an important clarification, not a gap:** in deterministic mode, agents are plain Python functions with no tool-calling loop, no shell access, no network access, and no filesystem access outside `agentic/artifact_store.py`. So controls like "agents cannot deploy to production" and "agent tools must be allowlisted" are satisfied **by construction** — there is no capability to misuse, not a runtime policy check we hope holds. This only becomes a real runtime-enforcement question if the optional live-LLM mode is ever turned on (an LLM-driven agent could attempt to call an arbitrary tool), so the live-LLM provider hook (`agentic/llm_provider.py`) is where an actual allowlist check belongs, if that mode is built out. This is flagged explicitly here so it isn't silently assumed solved for both modes — see ADR-011.

## 7. Observability

- Structured JSON logs to stdout (container-friendly; no log-rotation infra — that's a production concern, not a prototype one).
- Correlation ID: one per HTTP request (API), one per workflow run (orchestration) — both included in every log line and every error response.
- `workflow_events` is the durable, queryable audit trail (TRACE-02); stdout logs are for live debugging only, not the system of record.

## 8. Deployment Architecture

- `docker compose up --build` starts one service (`api`) on `:8000`, backed by a named volume for the SQLite file (data survives container restart).
- Alembic migrations run automatically on container start (idempotent, safe to re-run).
- Reviewer scenario/test commands run via `docker compose exec api ...` in the same container — no second container needed.

## 9. Key Decisions

See `docs/decisions/ADR-001` through `ADR-011` for full context/consequences/alternatives on each. Summary:

| ADR | Decision |
|---|---|
| 001 | Custom dependency-graph orchestrator, not a third-party agent framework |
| 002 | Single process/container hosts both API and orchestrator |
| 003 | Single SQLite file for application + orchestration tables |
| 004 | Deterministic agents by default; LLM is an optional pluggable provider |
| 005 | Workflow graph as an explicit in-code data structure |
| 006 | HTTP 307 for redirects |
| 007 | Added the missing SECURITY_REVIEW fail-path (corrects a master-brief diagram gap) |
| 008 | CLI-based approval only; workflow approval API deferred |
| 009 | Synchronous, resumable CLI execution — no background daemon |
| 010 | In-process concurrency (ThreadPoolExecutor) for the one parallel branch |
| 011 | Agent tool-allowlisting is satisfied by construction in deterministic mode; real enforcement only needed if live-LLM mode is built |

## 10. Risks and Mitigations (architecture-level, additive to requirements-baseline §17)

| Risk | Impact | Mitigation |
|---|---|---|
| Single SQLite file shared by app + orchestration tables could contend under concurrent scenario runs + live API traffic | Lock contention, flaky tests | Prototype scale only; documented production evolution path is to split into two databases/Postgres (§ backlog) |
| In-process ThreadPoolExecutor "parallelism" is not true process isolation | A crash in one branch could affect the other | Both branches are deterministic and side-effect-isolated (separate artifact writes); acceptable at prototype scale, called out explicitly rather than oversold as production-grade parallelism |
| Live-LLM mode's tool-allowlisting is architecturally deferred | If LLM mode is ever built without revisiting this, agent controls would be weaker than deterministic mode | ADR-011 flags this now so it can't be silently forgotten later |
